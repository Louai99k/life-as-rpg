## Playtest Goals

Playtesting exists to prove docs can run playable sessions with low friction and consistent logic. Goal is not only to find bugs, but to expose ambiguity, pacing drag, and scaling failure.

## Test Procedure

Each test should record:

- starting state
- mission or scenario used
- rules referenced
- results
- friction points
- unclear wording
- balance concerns

## Session Simulation Checklist

Each simulation should verify:

- startup speed
- mission generation speed
- encounter clarity
- requirement clarity
- reward clarity
- level-up behavior
- cleanup flow

## Problem Logging

Every identified issue should be logged with:

- short title
- affected chapter
- reproduction steps
- severity
- suspected cause
- proposed fix category

## Contradiction Review

Review must search for conflicts between chapters such as:

- glossary vs mechanics
- progression vs rewards
- tags vs encounter requirements
- gear rules vs ability set rules

## Balance Review

Balance review asks whether numbers, ranks, costs, and rewards match intended experience. It should use scenario-based checks, not intuition alone.

## Wording Review

Wording review checks whether someone can misread rule and still think they followed it correctly. If yes, wording is not done.

## Rule Conflict Resolution

When two rules conflict, revision process must decide priority order, usually:

1. glossary definition
2. core system rule
3. subsystem rule
4. oracle output
5. flavor text

## Revision Priority

Fix order should generally be:

1. contradictions
2. blockers to play
3. objective requirement failures
4. progression and balance issues
5. presentation issues

## Versioning Rules

Each meaningful rules change should record:

- version label
- date
- affected docs
- reason for change
- expected impact

## Approval Criteria

Chapter is stable enough for next phase when:

- terms are defined
- no known contradictions remain inside chapter
- chapter can be used in test session
- unresolved items are explicitly marked

## Freeze Conditions

System freeze for implementation work should happen only when core chapters are internally consistent and test sessions no longer reveal major structural errors.
